How it's built

Architecture & the reasoning behind it

A small ASP.NET Core Web API wrapping the AWS SDK for S3 bucket and object management. Below is the layering it follows, and the specific tradeoffs behind the choices that matter — not just which pattern was used, but what it replaced and why.

API

Controllers, request/response wiring

Core

IBucketRepository / IFilesRepository interfaces, own DTOs

Infrastructure

AWS SDK-backed implementation, mapped to Core DTOs

Design decisions

Own response DTOs (CreateBucketResponse, etc.) instead of returning AWS SDK types up through the API

instead of passing PutBucketResponse and other SDK response objects straight through to callers

The AWS SDK's response shapes change across major versions and carry AWS-specific metadata callers don't need. Mapping at the Infrastructure boundary means an SDK upgrade is a one-file change, not an API contract break — this repo's own migration from AWS SDK v3 to v4 only touched the Infrastructure layer.

Interface-driven IBucketRepository / IFilesRepository over the AWS SDK

instead of calling IAmazonS3 directly from the controllers

This is the case where the abstraction actually pays for itself: the object-storage backend legitimately varies — S3 here, a different cloud provider's storage on other projects — and the interface is what lets the same Core-layer contract carry across both without touching callers. If only one provider were ever expected for the life of a project, this layer wouldn't be worth adding — call the SDK directly from a thin service instead.

Endpoints

POST /api/bucket/create/{bucketName}Create an S3 bucket (rejects if it already exists)
GET /api/bucket/listList buckets
DELETE /api/bucket/delete/{bucketName}Delete a bucket
POST /api/files/{bucketName}/addUpload objects to a bucket
GET /api/files/{bucketName}/listList objects in a bucket
GET /api/files/{bucketName}/download/{fileName}Download an object
DELETE /api/files/{bucketName}/delete/{fileName}Delete an object
